# Portfolio Migration Plan

Source of truth for migrating the old CRA + Express portfolio into this Next.js project. We follow this plan phase by phase; each phase ends with a working, browser-verified result before moving to the next. Do not skip ahead or batch multiple phases together.

Old project: `C:\Users\ariel\Desktop\PROJECTS\_FINISHED\_React\portfolio (arielbehar.com)\_site`
Goal: same look and behavior as the old site, rendered as much as possible on the server, structured to modern Next.js best practices — not a lift-and-shift.

## Decisions locked in

- Tailwind v4 + DaisyUI instead of Material UI + Emotion.
- Next.js Server Actions instead of the standalone Express server.
- No animation library (no Framer Motion / Motion) — animations built with Tailwind utilities and custom CSS keyframes.
- Zod instead of Yup for the contact form's server-side validation.
- No React Hook Form — native `<form action>` + `useActionState`.
- No `uuid` for React keys — every data item already has a stable `_id`; use it.
- No `react-scroll` — native `scrollIntoView({ behavior: 'smooth' })` for nav links.
- `@react-three/fiber` v9 / `@react-three/drei` v10 confirmed compatible with React 19 — the Three.js avatar experience is being kept.
- Single-page "hero reveal on click, then scroll through sections" UX is preserved as-is (not being restructured into separate routes).
- Fonts: Saira (body) and Peralta (display headings) are genuine Google Fonts, loaded via `next/font/google`. Bangers is *also* loaded via `next/font/google` for any DOM/CSS text (`font-mesh` Tailwind class) — but the "I ♥ THREE JS" mesh inside the Three.js avatar scene needs a real, fetchable font-file URL (drei's `<Text>` can't consume a `next/font` object, which is CSS-only), so that specific usage restores the old self-hosted `public/fonts/bangers-v20-latin-regular.woff` instead. **Revised in Phase 7** after an HTML-overlay approximation of that same text was tried first and rejected as not matching closely enough — see Phase 7 notes.
- Mockup carousel: `embla-carousel-react` + `embla-carousel-autoplay` — decided and built in Phase 8 (see its notes for why).
- Harley Davidson 3D model is currently unused/commented out in the old code — decide keep-vs-drop when we reach Phase 7.

## Target folder structure

```
app/
  layout.tsx, page.tsx, globals.css
  actions/              # Server Actions (e.g. contact.ts) — lowercase, Next.js app/ convention
components/
  UI/                    # generic primitives (Button, Modal, Chip, etc.)
  Layout/                # Navigation, Footer, Loader
  Sections/              # one folder per portfolio section
utils/                   # helpers, consolidated into utils.ts + index.ts barrel (mailer, getChipColor, etc.)
data/                    # typed content, replacing the old *.json files
types/                   # shared TS interfaces
constants/               # nav links, external asset base URL, breakpoints
public/                  # only the binary assets actually needed locally
```

## Conventions (apply from Phase 1 onward)

- **`components/` subfolders are capitalized** (`UI`, `Layout`, `Sections`) — matches the PascalCase of the components they hold. Folders outside `components/` (`data`, `types`, `constants`, `lib`, `app/actions`) stay lowercase, following normal Next.js/TS convention.
- **Barrel exports everywhere they make sense**: every component gets its own folder with an `index.ts` re-exporting it (`components/UI/Button/index.ts` → `export * from './Button'`), and every category folder gets its own barrel (`components/UI/index.ts` aggregating everything under `UI/`). Same pattern for `constants/` and `types/` once they hold more than one file: an `index.ts` at the folder root re-exporting everything inside.
- **Alias imports everywhere**: use the `@/` path alias (already configured in `tsconfig.json`) instead of relative parent imports. This is a manual convention, not lint-enforced — no ESLint rule for it.

- **Found a real MUI `color` prop bug, traced to source — this recurs constantly in later sections**: the old `FlagCard.tsx` used `color='text.muted'` for the language proficiency numbers, and `AboutSection.tsx` used `color='text.muted.light'` for the footnote below the flags. Root-caused by reading MUI's actual source (`@mui/system/style.js`'s `getPath`, walking `theme.palette` by splitting the color string on `.`): `theme.palette.text = { primary, secondary, tertiary, muted: { main, light } }`. A path like `"text.muted.light"` or `"text.secondary"` walks all the way to a real hex string → valid CSS `color`, applied correctly. **Found and fixed six real bugs during build/verification, none present in any prior phase**:
1. **A 12-column CSS Grid (`grid-cols-12` + `col-span-7`/`col-span-5`) silently collapsed to zero-width tracks at the `lg` breakpoint.** `grid-template-columns: repeat(12, minmax(0,1fr))` reserves gap space at all 11 *internal track boundaries*, not just the one visually occupied between two spanning items — at `min-[1200px]:gap-44` (176px), `11 × 176px = 1936px` of reserved gap alone exceeded the entire `1152px` container, clamping every 1fr track to 0 and leaving both grid items to size themselves off their own content instead (overflowing the container substantially, pushing the right-hand card fully outside the 1280px viewport — this is what first surfaced the bug, as a "missing" second card in a screenshot). Root-caused via an isolated DOM-injection test confirming it reproduced with the exact class list outside any component context, then bisected by incrementally adding back each stacked `gap-*` breakpoint variant one at a time until the failure appeared. Fixed by switching from a 12-column integer grid to a genuine 2-column ratio grid (`grid-cols-[7fr_5fr]`), which has exactly one gap boundary and so works correctly at any gap size — items no longer need `col-span-*` at all. **Lesson for later phases**: a many-column integer grid is the wrong tool once the gap size becomes large relative to the container — prefer an explicit N-column `fr`-ratio template for a fixed small number of items.
2. **A `"use server"` file can only export async functions — a plain exported constant (`initialContactFormState`) crashed the entire page** with a Next.js build error the instant the Contact section rendered (confirmed via the dev server's console: `A "use server" file can only export async functions, found object`). Fixed by moving the trivial `{ status: "idle" }` initial state out of `app/actions/contact.ts` and into a local `const` inside `ContactForm.tsx`, its only consumer — `export type`/`export interface` declarations from the same file remain fine (erased entirely at compile time, so they were never actually the problem), only real *runtime* value exports are restricted.
3. **The HTML `pattern` attribute's regex failed to compile in the browser**, twice, for two different reasons in sequence. First: `[A-Za-z\s'-]+` alone threw `Invalid character in character class` — modern browsers compile the `pattern` attribute with the newer Unicode Sets (`v`) regex flag, which is stricter about a literal trailing hyphen sitting directly after a class-shorthand escape (`\s`) than the classic default flag is; escaping the hyphen explicitly (`\-`) resolves the ambiguity. Second, after that fix, the same error reappeared with visibly *doubled* backslashes in the compiled attribute — caused by writing `pattern="[A-Za-z\\s'\\-]+"` (JS-string-literal-style double-escaping) inside a **plain JSX string attribute**, which is not a JS string literal at all and receives no escape processing; the doubled backslashes were passed straight through into the DOM as two literal backslash characters each. Fixed to a single backslash per escape (`pattern="[A-Za-z\s'\-]+"`), confirmed via the DOM's actual `getAttribute('pattern')` value rather than reasoning about it abstractly a third time.
4. **`console.error("...", error)` on the Resend SDK's returned `ErrorResponse` object logged as an unhelpful empty `{}`** in the dev server's structured JSON log (`.next/dev/logs/next-development.log`), even though the object genuinely has `message`/`statusCode`/`name` fields — whatever serialization that log pipeline uses didn't surface them. Fixed by logging the specific fields directly (`error.name, error.statusCode, error.message`) instead of the object as a whole, which is what actually revealed the domain-verification 403 finding above. **Lesson**: don't trust `{}` in a log as "the error had no content" — try logging known fields explicitly before concluding an error is empty or unhelpful.
5. **The two cards' width ratio was visibly off, caught by Ariel from a side-by-side screenshot against the live old site.** A plain `grid-cols-[7fr_5fr]` (the fix from bug #1 above) renders a genuine 7:5 split of the space remaining *after* subtracting one shared gap — but that's not what MUI's Grid v1 actually produces from `sm={7}`/`sm={5}` with `spacing={22}`. MUI's negative-margin gutter technique expands the row by the *full* spacing value and gives each item that same spacing as its *own* padding (not half, shared) — the two adjacent items' paddings only *visually* read as a single gap; the real content-width formula per item is `(span/12)*(100% + G) - G`, not a simple post-gap fr-split. Measured on the live old site at 1920px: cards render `598.66px`/`377.33px` (ratio `1.587`), while `grid-cols-[7fr_5fr]` gives `569.33px`/`406.67px` (ratio `1.4`) — a real, visible difference, not a rounding artifact. Root-caused by algebraically reverse-engineering MUI's formula from the measured pixel values (confirmed to 3 decimal places), then reimplemented as plain flexbox with explicit `calc()` widths per breakpoint tier (`w-[calc(58.3333%-73.3333px)]` etc., one `G` value per old `spacing` tier: xs=16px/sm=24px/md=80px/lg=176px) plus a matching `ml-*` margin on the second card instead of a shared `gap` utility — re-verified at 1920px to render pixel-identical (`598.65625px`/`377.328125px`) to the old site. **Lesson**: MUI's legacy Grid v1 gutter math is not equivalent to modern CSS Grid's `gap`, even for values that look like they should produce the same visual ratio — when an old Grid's item proportions look visibly "more extreme" than the raw column-span fraction suggests, measure the actual rendered widths rather than assuming a modern `fr`/`gap` equivalent is exact.

**Note on the background photo's crop/zoom appearing to differ between screenshots**: `background-attachment: fixed` pins the image to the *viewport*, not the element — so the visible crop through a `bg-cover` fixed background depends on the page's exact scroll position when the screenshot is taken, not just the CSS (confirmed: `background-size`/`position`/`attachment` all measured identical between old and new). Since the old and new sites' cumulative page heights above Contact differ slightly (from dozens of small fidelity differences in every earlier section), the two sites land at slightly different scroll depths when Contact is scrolled to the top of the viewport, showing a different "window" into the same fixed image. This is expected/cosmetic, not a bug — confirmed by re-screenshotting the new site a second time and seeing the crop shift again on its own from a few pixels of scroll-position difference alone.

6. **Two more real padding bugs, both classic CSS margin-collapse, caught by Ariel from a second side-by-side screenshot ("fix the paddings").** Measured every internal gap on both cards at 1920px against the live old site and found two genuine ~24px discrepancies (everything else — card `padding`, field-row spacing, button-to-card-bottom, `emailLeftGap` — matched exactly): (a) both cards' headings measured `0px` from the card's own top edge instead of the intended `24px` (`my-6`'s top half not applying), and (b) the right card's email line measured `0px` from the card's bottom edge instead of `24px`. Root cause in both cases: the affected element is the first (or last) *in-flow* element inside a container with no padding on that same side (the left card's logo badge is `position:absolute`, so it doesn't count as in-flow for this purpose) — a block element's margin on that side collapses straight through the parent, landing *outside* the dark rounded background (in the transparent flex-item wrapper) instead of inside it. Fixed by moving that spacing from the child's own `mt-6`/`mb-6` to the *card's own* `pt-6`/`pb-6` (removing the now-redundant margin from the child) — padding, unlike margin, cannot collapse, so this is the correct general fix rather than a one-off patch. Re-verified all four gaps at 1920px to match the old site exactly (`24`/`24`/`80`/`24`). **Lesson**: this is the *same underlying category* of bug as bug #5's width-ratio issue and Documents' `SectionDivider` fix back in Phase 9 — a value that "should" be there per the props/classes present, but silently isn't because of a structural CSS mechanic (collapse, gutter math) rather than a wrong number. Measuring the actual rendered gap, not just re-reading the class list, is what catches these.

Used bundle inspection and real network-request tracing against `next build && next start` instead: the largest chunk (`~1.2MB`, confirmed by content signature to be Three.js/`react-three-fiber`) was loading on **every** initial page load, before the user had even clicked past the Hero splash — despite `AvatarSceneLoader.tsx` already using `next/dynamic({ssr:false})`. Fixed by gating `{children}`'s actual JSX presence on `revealed` (`{revealed && <div>...}`) instead of just toggling classes — re-verified via the same network-request trace that the Three.js chunk (and, as a side benefit, Photoshop's autoplaying TV video and its Embla carousel's autoplay timer) now only loads/starts after "Explore Site" is clicked, and confirmed the reveal transition itself still renders correctly (all sections present, zero console errors) after the change.
